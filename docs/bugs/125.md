# BUG-125 — C-API `lua_concat` left-to-right algorithm divergence

- **Severity:** [MED]
- **Status:** ⏳ OPEN

- **Location:** `src/lua.zig:5361-5396`; contrast with the corrected VM
  implementation documented at `src/lvm.zig:1351-1359`.
- **Defect:** The VM's `OP_CONCAT` was rewritten to fold right-to-left with
  maximal string runs (its comment explicitly records that the old loop "wrongly
  paired a leading non-string operand with itself"). `lua_concat` retains that
  old algorithm:
  - On meeting the first non-string/non-number operand it calls `__concat` once
    with `(previous_or_self, current)` and **returns immediately** — operands to
    its right are never folded, and the stack above `start+1` is left dirty;
  - when the first operand itself is non-stringish (`k == 0`), `p1 = p2 = val`,
    invoking the metamethod with the same value twice;
  - no `LUAI_MAXCCALLS` depth guard around metamethod recursion.
  C `luaV_concat` processes pairs until one string remains.
- **Impact:** Every auxlib/library caller of `lua_concat` (e.g. error-message
  assembly, `table.concat` fallbacks, custom builds) gets wrong results whenever
  any operand needs metamethod coercion, differing from both the port's own VM
  behavior and the reference.
- **Proposed fix:** Share one concatenation routine between the VM opcode and
  `lua_concat` (the VM version already has the right shape).
