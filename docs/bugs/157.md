# BUG-157 — `package.searchpath` With `init=".", sep="."` Returns the Bare Name

- **Severity:** `MED`
- **Status:** ✅ RESOLVED
- **Location:** `src/lib/loadlib.zig` (`searchpath` name-conversion helper)
- **Upstream failure:** `lua/testes/attrib.lua:138`

## Defect Summary

The reference name conversion (`lua/loadlib.c`, `searchpath`/`gsub` step)
replaces every character of `name` that is in the `init` set with `sep`, but
skips the replacement when the character equals `sep` itself:

```c
for (; *name; name++) {
  if (strchr(init, *name) != NULL && *name != *sep)
    luaL_addchar(&b, *sep);
  else
    luaL_addchar(&b, *name);
}
```

The port's result differs in the `init == sep == "."` case:

```
$ cd lua/testes
$ luazig -e 'print(package.searchpath("C.lua", "libs/?", "", ""))'   -- line 137: OK
libs/C.lua
$ luazig -e 'print(package.searchpath("C.lua", "libs/?", ".", "."))' -- line 138: BAD
C.lua                ← expected: libs/C.lua
```

The port appears to mangle the template/name join when the separator
substitution is a no-op (init char == sep char), losing the `libs/` prefix —
the returned string is the bare name, not the template-expanded path.

## Impact

`package.searchpath` with explicit `init`/`sep` arguments (used heavily by
module loaders and `attrib.lua`) returns the wrong path, so found modules are
misreported (`require` chains built on searchpath break) and upstream test
`attrib.lua:138` fails while line 137 passes.

## Resolution

The real defect was not in the name-conversion loop (that part was
faithful: `luaL_gsub(L, name, sep, dirsep)` replaces `sep` with `dirsep`,
matching `lua/lauxlib.c` `luaL_addgsub`) but in the stack bookkeeping of
`searchpath` (src/lib/loadlib.zig):

- `luaL_gsub` leaves its result on the stack. The normalization that follows
  used `lua_copy(L, -1, @intCast(initial_top + 1))` where `initial_top` is
  `L.top` (a raw stack-depth count), but positive Lua indices in this port
  are **frame-relative** (`ci.base + idx - 1`). The copy therefore landed
  on the wrong slot (often a no-op), and the gsub leftover ended up as the
  visible top value — the template was effectively dropped from the result
  whenever the conversion branch ran.
- Fixed by removing the leftover with the top-relative index
  (`lua_remove(L, -2)`) on both the found and not-found paths, so the
  result is a single value.

## Verification

- New unit test `BUG-157: package.searchpath name conversion (sep->dirsep)

  and single-value counts).
- Reproduced `lua/testes/attrib.lua:137-140` with the named files present:
  all four searchpath assertions pass.
