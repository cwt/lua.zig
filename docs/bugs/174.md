# BUG-174 — Interpreter ~2x Slower Than the C Reference

- **Severity:** `MED` (performance defect — no functional or conformance
  divergence; pi output matches the reference exactly)
- **Status:** ❌ OPEN
- **Location:** `src/lvm.zig` (`run` loop head + frame), `src/libm.zig`
  (`getLibm`), `src/lauxlib.zig` (`luaL_checknumber`),
  `src/lib/mathlib.zig` (call sites).

## Defect Summary

`tests/pi-5.5.lua` (100M iterations, ~23 opcodes + 2 C calls per iteration):

| Binary | Wall | Instructions |
|--------|------|--------------|
| C reference `./lua/lua` | 8.2s | 192B |
| luazig (ReleaseFast+thinLTO) | 15.5s | 425B |

The gap is pure instruction count (2.2x); luazig's IPC (5.2) is *higher*
than C's (4.5), so it is not branch-prediction or cache behavior.

## Root Causes (machine-confirmed)

See [Performance](../performance.md) for the full investigation,
disassembly evidence, and the ordered fix plan P1–P4.

- **RC1 (dominant):** `lvm.run` spills its loop state to a ~4.7KB stack
  frame (`subq $0x1258, %rsp`); per back-edge it reloads `g`, `L`, `code`
  from the frame and reads/stores `ci.savedpc` through memory. The C
  reference keeps a 104B frame with `L`/`ci`/`base`/`G`/`proto` pinned in
  callee-saved registers.
- **RC2:** the per-instruction GC check at `src/lvm.zig:727`
  (`g.gc_count > g.gc_threshold`, 3 pointer loads + 2 branches per opcode)
  has no counterpart in the C reference — `luaC_condGC` (`lua/lgc.h:233`)
  runs only at object-registration sites (`lua/lvm.c:1431/1637/1939` +
  C API/allocator sites).
- **RC3:** `luaL_checknumber`'s `!lua_Number` error-union call boundary
  (12.6% of total runtime; C's equivalent is ~10.3% with a longjmp error
  path that costs nothing on the hot path).
- **RC4:** `libm.getLibm()` returns the 14-function-pointer struct **by
  value** on every call (~112B copy + spills), at `mathlib` sites, VM
  `MOD` (`numMod`), and `POW`; C calls libm through the PLT directly.
- **RC5 (minor):** `anyerror` plumbing in hot opcode bodies.

## Impact

- ~1.9x wall-time on VM-arithmetic-bound workloads (the pi benchmark is
  worst-case: a tight pure-VM loop amplifying per-opcode overhead).
- Workloads dominated by I/O, GC, or table mutation show a smaller gap.

## Proposed Fix

Minimal-change plan P1–P4, see [Performance](../performance.md):

1. **P1** drop the per-instruction GC check; add `checkGC(L)` at the
   reference's object-registration sites (~15 lines, low risk).
2. **P2** loop-local `savedpc` + hoisted `hookmask` in `run` with a
   `savepc` sync audit (~40–60 lines, medium risk — the sync audit is the
   correctness-critical part; `locals.lua` is the tripwire).
3. **P3** `getLibm() -> *const Libm` (call sites unchanged; ~10 lines,
   no risk).
4. **P4** defer `luaL_checknumber` until re-measured.

Expected outcome: 425B → ~310–330B instructions (~10.5–11.5s, ≈1.3–1.4x C).

## Evidence

```
$ perf stat -e cycles,instructions,branches,branch-misses ./lua/lua tests/pi-5.5.lua
   43,226,342,342 cpu_core/cycles/u      192,158,513,762 cpu_core/instructions/u
   8.4s
$ perf stat -e cycles,instructions,branches,branch-misses ./zig-out/bin/luazig tests/pi-5.5.lua
   82,112,232,430 cpu_core/cycles/u      425,127,843,554 cpu_core/instructions/u
  16.1s
```

Per-opcode cost: ~118 instr/opcode (luazig) vs ~45 (C reference).
