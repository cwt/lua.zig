# BUG-174 — Interpreter ~2x Slower Than the C Reference

- **Severity:** `MED` (performance defect — no functional or conformance
  divergence; pi output matches the reference exactly)
- **Status:** ❌ OPEN — minimal-change pass P1–P4 **complete** (425B →
  375B, 15.5s → 12.7s, ≈1.55× C). The defect remains open: the residual
  gap to the C reference is the RC1 4.7KB `lvm.run` frame, which needs a
  deeper register-pinning pass (out of the minimal-change scope).
- **Location:** `src/lvm.zig` (`run` loop head + frame), `src/libm.zig`
  (`getLibm`), `src/lauxlib.zig` (`luaL_checknumber`),
  `src/lib/mathlib.zig` (call sites).

## Defect Summary

`tests/pi-5.5.lua` (100M iterations, ~23 opcodes + 2 C calls per iteration):

| Binary | Wall | Instructions |
|--------|------|--------------|
| C reference `./lua/lua` | 8.2s | 192B |
| luazig (ReleaseFast+thinLTO) | 15.5s | 425B |

The gap is pure instruction count (2.2x); luazig's IPC (5.2) is *higher*
than C's (4.5), so it is not branch-prediction or cache behavior.

## Root Causes (machine-confirmed)

See [Performance](../performance.md) for the full investigation,
disassembly evidence, and the ordered fix plan P1–P4.

- **RC1 (dominant):** `lvm.run` spills its loop state to a ~4.7KB stack
  frame (`subq $0x1258, %rsp`); per back-edge it reloads `g`, `L`, `code`
  from the frame and reads/stores `ci.savedpc` through memory. The C
  reference keeps a 104B frame with `L`/`ci`/`base`/`G`/`proto` pinned in
  callee-saved registers.
- **RC2:** the per-instruction GC check at `src/lvm.zig:727`
  (`g.gc_count > g.gc_threshold`, 3 pointer loads + 2 branches per opcode)
  has no counterpart in the C reference — `luaC_condGC` (`lua/lgc.h:233`)
  runs only at object-registration sites (`lua/lvm.c:1431/1637/1939` +
  C API/allocator sites).
- **RC3:** `luaL_checknumber`'s `!lua_Number` error-union call boundary
  (12.6% of total runtime; C's equivalent is ~10.3% with a longjmp error
  path that costs nothing on the hot path).
- **RC4:** `libm.getLibm()` returns the 14-function-pointer struct **by
  value** on every call (~112B copy + spills), at `mathlib` sites, VM
  `MOD` (`numMod`), and `POW`; C calls libm through the PLT directly.
- **RC5 (minor):** `anyerror` plumbing in hot opcode bodies.

## Impact

- ~1.9x wall-time on VM-arithmetic-bound workloads (the pi benchmark is
  worst-case: a tight pure-VM loop amplifying per-opcode overhead).
- Workloads dominated by I/O, GC, or table mutation show a smaller gap.

## Proposed Fix

Minimal-change plan P1–P4, see [Performance](../performance.md):

1. **P1** ✅ DONE — drop the per-instruction GC check; `luaC_checkGC` at
   the reference's VM sites (NEWTABLE/CONCAT/CLOSURE, check **after**
   anchoring the new object on the stack) + `luaC_condGC` at the
   C-API/lexer/parser sites. Result: 425B → 397B instructions.
2. **P2** ✅ DONE — loop-local `pc` + hoisted `hookmask` in `run` (sync at
   the 57 error-capable arms + frame switches; `docondjump` reworked).
   Wall time 15.2 → 14.66s (~1.79× C), but instruction count rose 397 →
   403B (sync/reload sites offset the back-edge win; the 4.7KB frame /
   register-pinning issue from RC1 remains — deeper follow-up).
 3. **P3** ✅ DONE — `getLibm() -> *const Libm` (pointer to a
    process-lifetime singleton, not a 112-byte by-value copy; call sites
    unchanged). Result: 403B → 394B instructions, 14.6s → 13.8s wall.
 4. **P4** ✅ DONE — re-measured (still the #2 hot leaf, ~22%), then the
    non-error fast path: every mathlib numeric-arg read is now
    `lua.lua_tonumber(L, N) orelse try luaL_checknumber(L, N)` (22 sites,
    provably behavior-identical). Result: 394B → 375B instructions,
    13.8s → 12.7s wall; `luaL_checknumber` no longer a hot frame.

 Expected outcome: the minimal-change pass (P1–P4) is complete. 425B /
 15.5s → **375B / 12.7s (≈1.55× C)** (vs 192B / 8.2s for the C reference):
 −50B instructions (−12%) and −2.8s wall with byte-identical output and the
 upstream suite held at 20 PASS / 0 FAIL / 0 CRASH. P1/P3/P4 landed at or
 near their estimates; P2 improved wall time but raised the instruction
 count (sync/reload sites), so the ~4.4KB `lvm.run` frame remains. The
 residual gap is the RC1/RC5 deep pass now **planned as D1–D4** in
 `docs/performance.md` (strip the `!` error-union ABI off the hot VM
 helper-call paths — `precall`/`poscall`/`luaT_*`/`closeupvals`/
 `checkclosemth` — P4-style; the frame should then shrink and the backend
 pin the loop state). Not yet implemented.

 Update (2026-09-10): D1 done; D2 (precall ABI split) **attempted and
 reverted** — measured −0.8B / +0.2s (projection falsified); the backend
 re-spills the loop-state frame mirrors, so the real lever is D4
 (structural register-pressure reduction), deferred. State remains P4:
 375B / 12.7s ≈ 1.55× C.
