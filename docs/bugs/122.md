# BUG-122 — `lua.zig`: unguarded stack writes while closing TBC variables

- **Severity:** [HIGH]
- **Status:** ⏳ OPEN

- **Location:** `src/lua.zig:543-615` (`closeupvals`, top raise at 582-584),
  `454-541` (`close_one_slot`, writes at 468-478, 504, 527, 533).
- **Defect:** To keep TBC slots visible to a GC triggered inside `__close`,
  `closeupvals` sets `L.top = @max(L.top, abs + 1)`. A to-be-closed variable in
  the final usable slot makes `abs + 1 == L.stack.len`; `close_one_slot` then
  executes `L.stack[L.top] = ...` (error string pushes) with no
  `lua_checkstack`-style capacity check → out-of-bounds write (panic in Debug,
  heap corruption in ReleaseFast). The C reference keeps EXTRA_STACK (5 slots)
  beyond `stack_last` precisely for such emergency writes and still checks.
- **Impact:** Rare but fatal: closing a `__close` variable allocated at the very
  top of the stack (e.g. deep recursion ending in `<close>` locals, or error
  unwinding near stack exhaustion) corrupts the heap or panics instead of raising
  a Lua error.
- **Proposed fix:** Guarantee headroom before running closers
  (`reserveErrorStack`-style growth), and clamp `gc_safe_top` to
  `stack.len - 1` while ensuring marking coverage another way.
