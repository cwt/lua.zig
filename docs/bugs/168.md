# BUG-168 — Double-Free When `__close` Closes the Thread Being Closed

- **Severity:** `CRITICAL` (memory corruption / process abort)
- **Status:** ✅ RESOLVED
- **Location:** `src/lua.zig` (`lua_closethread` / `closeupvals` / thread free
  path) interacting with `src/lib/corolib.zig` (`luaB_close`).
- **Upstream failure:** `lua/testes/coroutine.lua:174-187` ("close a
  coroutine while closing it").

## Defect Summary

```lua
local function func2close (f)
  return setmetatable({}, {__close = f})
end
co = coroutine.create(
  function()
    local x <close> = func2close(function()
        coroutine.close(co)   -- close it again, from inside __close
     end)
    coroutine.yield(20)
  end)
assert(select(2, coroutine.resume(co)) == 20)
local st, msg = coroutine.close(co)
assert(st and msg == nil)
```

In the C reference this asserts cleanly. In luazig the second
`coroutine.close(co)` (entered from *inside* the `__close` metamethod that
`coroutine.close(co)` is already running) leads to a double free of the
thread / its CallInfo / stack and a glibc abort:

```
free(): double free detected in tcache 2
```

## Impact

- Any user program that closes a coroutine from within its own `__close`
  metamethod (a documented pattern for "close-again is a no-op") crashes the
  whole process instead of returning `(true, nil)`.
- Blocks `lua/testes/coroutine.lua` from passing standalone (it now reaches the
  `coroutine.close` section after [BUG-156](156.md) was fixed).

## Proposed Fix

Trace the `coroutine.close` → `lua_closethread` → `closeupvals` →
`close_one_slot` → `__close` → nested `coroutine.close` re-entry. Ensure the
thread object / CallInfo chain / stack are released exactly once: guard the
nested close as a no-op once the thread is already marked closed/dead, and make
`lua_close`/`lua_closethread` idempotent for an already-closed thread.

## Resolution

The crash came from a re-entrant `lua_closethread`: a `__close` that calls
`coroutine.close(co)` on the thread being closed re-entered the close path and
the nested call's `freeAllCallInfos` destroyed the live CallInfo chain that the
outer close (and its `__close` C frames, whose `luaT_callTM*` handlers keep a
pointer to `old_ci`) still used. Fixed in `src/lua.zig` + `src/lib/corolib.zig`:

1. **`close_in_progress` re-entrancy guard** on `lua_State`. The outer
   `lua_closethread` sets it before `closeupvals`; a nested self-close sees it
   and skips the destructive teardown, just finalizing the status.
2. **`close_err_consumed` flag**: a closed thread's pending error is reported
   exactly once; a re-close is clean (`coroutine.lua` "after closing, no more
   errors").
3. **Self-close skips `freeAllCallInfos`, uses `recycleCallInfos`** (moves the
   chain to the freelist, resets `L.ci` to base, no destroy) so the active
   frames the `error.ThreadClosed` unwind traverses are not freed underfoot,
   and `lua_resume` computes a zero result count.
4. **`close_one_slot`/`closeupvals`** treat `error.ThreadClosed` (a `__close`
   self-close) as a clean self-close, not a close error, so the outer close
   still returns `(true, nil)`.
5. **`corolib.luaB_close` COS_RUN** self-close propagates `error.ThreadClosed`
   (modeling the reference's non-local `luaD_throwbaselevel`), so the line
   after `coroutine.close()` in the coroutine body does not execute and any
   intermediate pcall catches it.

## Verification

- No more `free(): double free` abort; `coroutine.lua` proceeds through the
  entire `coroutine.close` section (lines 140-330) without crashing.
- New unit test `BUG-168: coroutine self-close and re-close are safe (no
  double-free/UAF)` in `tests/test_basic.zig` covering the three sub-cases
  plus a post-close GC.
- `zig build test` → all tests passing, 0 leaks. `./run_testes.sh` → 20 PASS / 0
  FAIL / 0 CRASH.

Note: `coroutine.lua` standalone now fails later (line 380) on an unrelated
yield-in-`xpcall`-across-C-boundary conformance gap (the BUG-160/162 family),
not on any close/memory issue.
