# BUG-115 — `io.popen` was a stub: always returned `(nil, "'popen' not supported")`

- **Severity:** [HIGH]
- **Status:** ✅ FIXED

- **Location:** `src/lib/iolib.zig:203-207` (`io_popen`); missing `io_pclose` close handler.
- **Defect:** `io_popen` was a stub that unconditionally returned `nil` with the error message `"'popen' not supported"`. The C reference (`lua/liolib.c`) uses POSIX `popen()`/`pclose()` (or Windows `_popen`/`_pclose`). No child process was spawned and no pipe fds were managed. Related, `io_pclose` (the `__gc` / explicit-close handler for popen streams) did not exist, so even if a fd-wrapping approach had been used, zombie processes would have accumulated.
- **Impact:** Any Lua program using `io.popen(...)` received `(nil, "'popen' not supported")`. Scripts like `fire.lua` that depend on `io.popen("tput cols")` to discover terminal dimensions crashed immediately (`attempt to index a nil value`). All standard-library code and upstream tests relying on popen (e.g. `cos test.lua`'s `io.popen` smoke tests) were silently broken. Latent because the test suite never exercised it.
- **Fix:** Implemented `io_popen` using `std.process.spawn` with `.stdin = .pipe` / `.stdout = .pipe` options (matching C semantics: mode `"r"` → child stdout is parent's read fd; mode `"w"` → child stdin is parent's write fd). Added a `child: ?std.process.Child` field to `LStream` to track the spawned process. Implemented `io_pclose` as the close handler: it calls `child.wait(io)` to reap the child (returning the exit-status triple via `luaL_execresult`, matching the C reference), then closes the pipe fd. Updated `doClose` to also reap the child when present (prevents zombies if the user forgets to call `:close()`). Mode validation now rejects `"r+"`/`"w+"`/`"rb"` (matching the C reference's `l_checkmodep` which accepts only bare `"r"` or `"w"`). Verified: `io.popen("echo hello"):read("*a")` → `"hello\n"`; `io.popen("tput cols"):read("*n")` → `80`; `fire.lua` runs end-to-end. **2026-08-14**.
