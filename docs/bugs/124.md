# BUG-124 — `lua_rawequal` semantic divergences

- **Severity:** [MED]
- **Status:** ✅ FIXED

- **Location:** `src/lua.zig:1928-1958`.
- **Defect:**
  1. Line 1931 returns 0 when tags differ, so `rawequal(1, 1.0)` → false.
     The reference compares all numbers by value (`luaV_rawequalobj`).
     Differential test confirms the divergence.
  2. Strings are compared by optional-pointer identity only (line 1937). Long
     strings (>40 chars) are not interned in this port or in C, so two equal-content
     long strings can be distinct objects — C still reports them equal via
     content comparison (`luaS_eqstr`), the port does not.
  3. Lines 1943-1947 invent value equality for C functions: two *distinct*
     closures with the same `f` and no upvalues compare equal. In the reference,
     C function equality is pointer identity only.
- **Impact:** Wrong results for ordinary Lua programs using `rawequal` on mixed
  numeric types or on long strings; behavioral divergence for embedding code that
  distinguishes separate pushes of the same C function.
- **Proposed fix:** Delegate to a shared primitive-equality helper (the port's own
  `tvEqual` at lua.zig:3764 already handles int/float and string content
  correctly) and delete the C-closure special case.
- **Fix:** Implemented `luaV_rawequalobj` in `src/lua.zig` matching `lvm.c:luaV_rawequalobj`, delegated `lua_rawequal` to it, and removed invented C-closure equality from `src/lua.zig` and `src/ltm.zig`. Added unit test in `tests/test_basic.zig`.
