# BUG-160 — Yield From a Resumed Coroutine Metamethod Chain Mis-Tracked

- **Severity:** `HIGH`
- **Status:** ❌ OPEN
- **Location:** `src/lvm.zig` (resume continuation path) / `src/lua.zig` (`noyield` counter, ~line 1214-1218) / `src/ltm.zig` (metamethod dispatch)
- **Upstream failure:** `lua/testes/big.lua:56`

## Defect Summary

`big.lua` (lines 29-56) exercises yielding from `__index`/`__newindex`
metamethods inside a wrapped coroutine:

```lua
__index = function (t, n) coroutine.yield('g'); return _G[n] end,
...
local co = coroutine.wrap(f)
...
coroutine.yield'b'    -- big.lua:56 — works in the reference
```

The port fails with:

```
[C]: in global 'error'
[C]: in field 'yield'
big.lua:56: in main chunk
luazig: big.lua: attempt to yield from outside a coroutine
```

The port's yield-eligibility check rejects a yield that the reference
performs. The port tracks yieldability with a separate `noyield: u32` counter
on `lua_State` (structurally splitting what C packs into the high bits of
`nCcalls`); somewhere along the resume → metamethod dispatch (`luaT_callTM1`)
→ `yield` path the counter is left incremented (or the resumable context is
not marked), so `yield` believes it is outside a coroutine.

## Impact

- `lua/testes/big.lua` (heavy test, harness-skipped) fails.
- Any program yielding from metamethods triggered by field access inside a
  resumed coroutine — a documented, supported Lua pattern — errors out.

## Proposed Fix

1. Trace the `noyield`/`nCcalls` adjustments around `lua_resume` and
   `luaT_callTM1`/`luaT_callTM2` in `src/ltm.zig`; the counter must be
   decremented/eligible while running inside a resumed coroutine.
2. Mirror the C invariant: `nCcalls` (incl. Cnumyield bits) is *saved and
   restored* around protected calls, not reset.
3. Add a focused regression test: resume a coroutine whose `__index`
   metamethod yields.
