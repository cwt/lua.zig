# BUG-155 — `posrelatI` Maps `pos == 0` to 0 Instead of 1: `string.sub` Reads One Byte Before the String

- **Severity:** `HIGH`
- **Status:** ✅ RESOLVED
- **Location:** `src/lib/string/pattern.zig:27-35` (`posrelatI`), consumed by `src/lib/stringlib.zig:25-36` (`str_sub`)
- **Upstream failure:** `lua/testes/strings.lua:44`

## Defect Summary

The Zig port of `posrelatI` (src/lib/string/pattern.zig:27):

```zig
pub fn posrelatI(pos: i64, len: usize) usize {
    if (pos >= 0) {
        return @as(usize, @intCast(pos));   // pos == 0 → 0  ❌
    } else { ... }
}
```

The C reference (`lua/lstrlib.c`, `posrelatI`):

```c
static lua_Integer posrelatI (lua_Integer pos, size_t len) {
  if (pos > 0) return pos;
  else if (pos == 0) return 1;  /* begin from the start */  ← missing in port
  else if (pos < -(lua_Integer)len) return 1;  /* clip it to 1 */  ← also missing
  else return (lua_Integer)len + pos + 1;
}
```

Two divergences:

1. `pos == 0` must map to `1` (start positions), not `0`.
2. Out-of-range negative (`pos < -len`) must clip to `1`, not `0`.

## Impact

`str_sub` (src/lib/stringlib.zig:30-31) computes the slice as `s[start - 1 .. end]`.
With the buggy `start == 0`, the slice arithmetic becomes `s[0 - 1 .. end]` — an
underflowed `usize` start index. The project's default build is **ReleaseFast**
(`build.zig:15-18`), which disables slice bounds checks, so this does not
panic; it silently reads **one byte before the string data** (interning
metadata):

```
$ luazig -e 'print("[" .. string.sub("123456789",0,0) .. "]")'
[ ]              ← expected: []
$ luazig -e 'print("[" .. string.sub("123456789",-10,10) .. "]")'
[ 123456789]     ← expected: [123456789]
```

Every `string.*` function that indexes through `posrelatI` with a start
position of `0` or an out-of-range negative start (e.g. `str_byte`, `str_rep`
call sites) is affected. A Debug/ReleaseSafe build would panic with an integer
underflow instead — still wrong, just louder.

## Evidence

- Upstream `lua/testes/strings.lua` fails at line 44 (`assert(string.sub("123456789",0,0) == "")`) when run standalone:
  `cd lua/testes && ../../zig-out/bin/luazig strings.lua` → `assertion failed!` at `strings.lua:44`.
- `getendpos` (src/lib/string/pattern.zig:37-44) is correct for `pos == 0`
  (C returns 0 for end positions) — only `posrelatI` diverges.

## Proposed Fix

Mirror the C clamps exactly in `posrelatI`:

```zig
pub fn posrelatI(pos: i64, len: usize) usize {
    if (pos > 0) return @intCast(pos);
    if (pos == 0) return 1;
    const slen: i64 = @intCast(len);
    if (pos < -slen) return 1;              // clip to start
    return @intCast(slen + pos + 1);
}
```

Then audit all call sites (`str_sub`, `str_byte`, `str_rep`, pattern match
ranges) so that start positions use `posrelatI` and end positions use
`getendpos`, per the C reference.

## Resolution

In `src/lib/string/pattern.zig`, updated `posrelatI` to match the C reference (`lua/lstrlib.c`):
- Explicitly map `pos == 0` to `1` (start position).
- Explicitly clip negative positions out of range (`pos < -len`) to `1`.

```zig
pub fn posrelatI(pos: i64, len: usize) usize {
    if (pos > 0) {
        return @as(usize, @intCast(pos));
    } else if (pos == 0) {
        return 1;
    } else {
        const slen = @as(i64, @intCast(len));
        if (pos < -slen) return 1;
        return @as(usize, @intCast(slen + pos + 1));
    }
}
```

## Verification

- Added unit test `BUG-155: posrelatI clips pos==0 and pos<-len to 1` in `tests/test_basic.zig`.
- Standalone `strings.lua:44` (`assert(string.sub("123456789",0,0) == "")`) verified passing.
- `zig build test` passes.

## Related

- End-position helper `getendpos` is faithful; do not "fix" its `pos == 0 → 0` case.
- Discovered while re-running the upstream `lua/testes/` suite standalone (2026-09-08); see also [BUG-166](166.md) on harness skip blind spots.
