# BUG-140 — `pushclosure` Missing `errdefer` Causes Sequential Heap Leaks on OOM

- **Severity:** `HIGH`
- **Status:** ⏳ OPEN
- **Location:** `src/lvm.zig:1870-1892` (`pushclosure`)

## Defect Summary

`pushclosure` performs multiple fallible heap operations in sequence without `errdefer` unwinding handlers:
```zig
const lc = try L.allocator.create(lua.lua_LClosure);
const upvals = try L.allocator.alloc(?*lua.UpVal, p.upvalues.len);
@memset(upvals, null);
lc.* = .{
    .p = p,
    .upvals = upvals,
};
for (p.upvalues, 0..) |uv_desc, k| {
    if (uv_desc.instack != 0) {
        lc.upvals[k] = try lua.findupval(L, base + uv_desc.idx);
    } else {
        lc.upvals[k] = encup[uv_desc.idx];
    }
    if (lc.upvals[k]) |uv| {
        uv.refcount += 1;
    }
}
const cl = try L.allocator.create(lua.lua_Closure);
cl.* = .{ .lua = lc };
try lua.registerGC(L, cl);
```

If an allocation fails:
1. When `upvals` allocation fails: `lc` is leaked.
2. When `findupval` fails inside the loop: both `lc` and `upvals` leak. Moreover, any upvalues in `lc.upvals[0..k]` whose `refcount` was already incremented are not decremented, leaking upvalue nodes.
3. When `cl` allocation fails: `lc` and `upvals` leak, and all captured upvalue refcounts remain permanently incremented.
4. When `registerGC(L, cl)` fails: `cl`, `lc`, and `upvals` all leak.

## Impact

Under out-of-memory pressure during bytecode execution (`OP_CLOSURE`), repeated closure instantiation attempts leak memory buffers and artificially pin upvalues in memory via orphaned reference counts.

## Proposed Fix

Add appropriate `errdefer` guards and cleanup logic:
1. `errdefer L.allocator.destroy(lc);`
2. `errdefer L.allocator.free(upvals);`
3. If `findupval` fails, roll back `refcount` increments on already captured upvalues.
4. `errdefer L.allocator.destroy(cl);` before calling `registerGC`.
