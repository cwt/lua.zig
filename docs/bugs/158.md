# BUG-158 — `collectgarbage("generational")` Does Not Return the Previous GC Mode

- **Severity:** `MED`
- **Status:** ✅ RESOLVED
- **Location:** `src/lua.zig` (`lua_gc` / `LUA_GCGEN` / `LUA_GCINC` handling, ~line 5263-5269) and `src/lib/baselib.zig` (`collectgarbage` mode strings)
- **Upstream failure:** `lua/testes/gc.lua:15`

## Defect Summary

Upstream `gc.lua:14-15`:

```lua
-- changing modes should return previous mode
assert(collectgarbage("generational") == "incremental")
assert(collectgarbage("generational") == "generational")
```

In the C reference, `collectgarbage("generational")` switches the collector to
generational mode **and returns the string name of the previous mode**
(`"incremental"`), and switching back returns `"generational"`. The port
(Phase H.10, see AGENTS.md §H.10) only *acknowledges* the mode switch while
keeping the mark-and-sweep engine, and does not return the previous-mode
string.

## Impact

`lua/testes/gc.lua` fails at line 15 when run standalone. The round-trip
semantics (`collectgarbage` returning the old mode) is a documented C-API
contract, so embedded consumers relying on it silently get wrong values.

## Context

This is a conformance-visible consequence of the documented Phase H.10
simplification (generational mode not implemented; `LUA_GCGEN`/`LUA_GCINC`
acknowledge only). Even without a true generational collector, the **return
value** can be made conformant by tracking a mode flag
(`incremental`/`generational`) in `global_State` and returning its previous
value on a switch.

## Resolution

1. **`global_State.gc_mode` field added** (`src/lua.zig`): tracks the active
   mode (`LUA_GCINC` default / `LUA_GCGEN`), mirroring the C reference's
   `g->gckind` (only the label is tracked; the engine remains mark-and-sweep,
   per the documented Phase H.10 scope).
2. **`lua_gc`** (`LUA_GCGEN` / `LUA_GCINC`) now returns the *previous* mode
   constant and switches to the requested one — a faithful port of
   `lua/lapi.c` `case LUA_GCGEN/GCINC`.
3. **`collectgarbage`** (`src/lib/baselib.zig`) gained a dedicated
   `LUA_GCGEN`/`LUA_GCINC` case porting the C `pushmode` helper: it pushes the
   previous mode's string name (`"incremental"`/`"generational"`), or fails
   when `lua_gc` returned `-1`.

## Verification

- New unit test `BUG-158: collectgarbage generational/incremental returns the
  previous mode` in `tests/test_basic.zig` (the gc.lua:14-15 round-trip plus
  the other options).
- `lua/testes/gc.lua:14-15` now passes standalone (the file proceeds past the
  mode round-trip; a separate GC step-counting defect at gc.lua:71 is tracked
  independently as [BUG-169](169.md)).
- `zig build test` → all tests pass, 0 leaks. `./run_testes.sh` → 20 PASS / 0
  FAIL / 0 CRASH.
