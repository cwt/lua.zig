# BUG-120 — `lua.zig`: coroutines are never collected by the GC

- **Severity:** [HIGH]
- **Status:** ✅ FIXED

- **Location:** `src/lua.zig:1046-1066` (`VMGCObject.ValUnion` has no `.thread`
  variant), `2266-2309` (`lua_newthread` never calls `registerGC`),
  `4526-4542` (`markValue` ignores `.thread`), `4680-4736` (`freeGCObject` has no
  thread arm), `5922-5931` (threads freed only from `thread_list` at
  `lua_close`). Dead calls that assume otherwise: `getGCObject(g, th)` at 4903
  and the `.thread` arm of `getGCObjectFromValue` (4766) always return null.
- **Defect:** Created coroutines exist outside the mark/sweep object graph. An
  unreachable coroutine (and its stack, CallInfo pool, TBC list) can never be
  reclaimed while the state lives. The C reference treats threads as first-class
  GC objects (`lgc.c` `freeobj` `LUA_TTHREAD`, traverseThread).
- **Impact:** Unbounded memory growth in workloads that spawn short-lived
  coroutines (generators, per-request handlers). Also means `collectgarbage("count")`
  under-reports and the count-based GC threshold never reacts to coroutine churn.
  No UAF today because sweep never sees threads — but any future integration
  (e.g. weak tables holding threads) would dangle.
- **Proposed fix:** Add a `.thread` variant to `VMGCObject`, register threads,
  mark their stacks/open upvalues during traversal, and free dead ones in sweep;
  keep the main thread as an unconditional root as in C.
- **Fix:** Added `.thread` variant to `VMGCObject.ValUnion`, registered coroutines in `registerGC` in `lua_newthread`, wired thread traversal in `traverseGrayObject` and cleanup in `freeGCObject`, and rooted `mainthread` in `luaC_collectgarbage`. Added unit test in `tests/test_basic.zig`.
