# BUG-123 — float→string via `{d}` with undersized buffers (silent data loss)

- **Severity:** [HIGH]
- **Status:** ✅ FIXED

- **Location:** `src/lvm.zig:1374-1381` (`OP_CONCAT`, `bufPrint("{d}")` into
  `[64]u8` / `[32]u8` with `catch ""`), `src/lua.zig:1697-1704`
  (`lua_tolstring`, `catch return null`), `src/lua.zig:5375-5379` (`lua_concat`),
  `src/lib/iolib.zig:632-639` (`g_write`). Correct formatter exists but is
  bypassed: `src/lauxlib.zig:332` (`tostringbuffFloat`, used by
  `luaL_tolstring`/`print`).
- **Defect:** Four separate paths convert numbers to strings with Zig's `{d}`
  rather than the Lua number-to-string algorithm. Verified differentially:
  - VM concat: `100*1e300 .. "!"` yields `"!"` — the 300-digit `{d}` expansion
    overflows the 64-byte buffer and `catch ""` silently substitutes an empty
    string (data corruption, no error).
  - `io.write(1e15)` prints `1000000000000000`; reference prints `1e+15`.
    `io.write(1e300)` prints a 301-digit expansion; reference prints `1e+300`.
  - `lua_tolstring` on such floats returns `null` (conversion failure) where C
    always produces a string.
  - C-API `lua_concat` propagates `error.OutOfMemory` from `bufPrint` where C
    succeeds.
  This supersedes the cosmetic framing of BUG-014 (closed WON'T FIX): the
  buffer-overflow path makes it a correctness bug, not just formatting taste.
- **Impact:** Silent wrong results in string building; observable output
  divergence through `io.write`; API contract breakage in `lua_tolstring`.
- **Proposed fix:** Route all four sites through one shared
  number-to-string helper implementing the LUAI_NUMFFORMAT ("%.14g"-style)
  algorithm (reuse `tostringbuffFloat`); remove the `catch ""` /
  `catch unreachable` fallbacks.
- **Fix:** Implemented `luaO_tostringbuff` and `tostringbuffFloat` in `src/lua.zig`, and routed `OP_CONCAT`, `lua_tolstring`, `lua_concat`, and `iolib` `g_write` through it with 128-byte buffers. Added unit tests in `tests/test_basic.zig`.
