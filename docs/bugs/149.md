# BUG-149 — `string.format` Raises Divergent Error Message for 3-Digit Width/Precision Specifiers

- **Severity:** `LOW`
- **Status:** ✅ FIXED
- **Location:** `src/lib/string/format.zig:10-22` (`get2digits`), main loop `src/lib/string/format.zig:530-636`

## Defect Summary

In `src/lib/string/format.zig`:
```zig
fn get2digits(s: []const u8, pos: usize) struct { val: i32, new_pos: usize } {
    var val: i32 = 0;
    var p = pos;
    if (p < s.len and std.ascii.isDigit(s[p])) {
        val = @as(i32, @intCast(s[p] - '0'));
        p += 1;
    }
    if (p < s.len and std.ascii.isDigit(s[p])) {
        val = val * 10 + @as(i32, @intCast(s[p] - '0'));
        p += 1;
    }
    return .{ .val = val, .new_pos = p };
}
```

The function only parses at most 2 digits.

**Important context (validated against the reference):** the C reference has the
*same* 2-digit limit — `lua/lstrlib.c:1220-1226` (`get2digits`, comment
`"(2 digits at most)"`), and `checkformat` (`lstrlib.c:1235-1248`) raises an
error when a non-alpha character remains after skipping 2 digits. So widths or
precisions of 100 or greater **are rejected by the reference too**; supporting
them (e.g. via a general integer parser) would *diverge* from the reference.

The actual defect is therefore only the error message. For
`string.format("%100s", "hello")`:
- `get2digits` parses `'1'` and `'0'`, returning `val = 10` and `new_pos = pos + 2`.
- The third digit `'0'` is left unconsumed in the format string.
- The format loop expects a conversion specifier (`s`, `d`, etc.) at `new_pos`, but encounters `'0'`.
- luazig raises: `"invalid conversion '%0' to 'format'"` (main-loop fallthrough, `format.zig:636`).
- The reference raises: `"invalid conversion specification: '%100s'"` (`lstrlib.c:1247`).

## Impact

Conformance divergence only: scripts matching on the reference error message
(e.g. upstream `lua/testes/strings.lua` style checks) fail. The accept/reject
behavior itself matches the reference.

## Proposed Fix

Keep the 2-digit limit (it matches the reference). Fix only the error path so
that when the format loop encounters an unexpected character after the width or
precision digits, it raises the reference message:

```zig
return lauxlib.luaL_error(L, "invalid conversion specification: '{s}'", full_spec_slice);
```

i.e. detect the "digit where a specifier was expected" case and report the
whole conversion specification (from `%` through the offending character), not
just `'%<char>'`.
