# BUG-127 — `ltable.asInt` float-key range too narrow

- **Severity:** [MED]
- **Status:** ✅ FIXED

- **Location:** `src/ltable.zig:30-37` (`asInt`).
- **Defect:** `asInt` bails out when `n < -9.0e18 or n > 9.0e18`, but
  `lua_Integer` extends to ±(2^63−1) ≈ ±9.2233720368547758e18. Integral floats in
  `(9e18, 2^63)` exist (spacing 2048 there) and the reference converts them via
  `luaV_flttointeger(..., F2Ieq)` (`lua/ltable.c:1030-1035`) into integer keys.
  The port stores them as *float* hash keys instead.
- **Impact:**
  - `pairs` yields such keys as floats (`9.1e+18`) where the reference yields
    integers;
  - `#t` border search uses integer probes (`hashHasInt`), so borders involving
    these keys are computed differently;
  - cross-type lookup still succeeds only because `keyEquals` falls back to
    numeric comparison — masking the storage divergence.
- **Proposed fix:** Replace the fixed 9.0e18 bound with an exact
  fits-in-i64 check (compare against 2^63 boundaries or use
  `@floor(n) == n and n >= -9223372036854775808.0 and n < 9223372036854775808.0`)
  before `@intFromFloat`.
- **Fix:** Delegated `ltable.asInt` to `TValue.toIntegerExactOpt()` which checks exact representation across the entire `[-2^63, 2^63)` float range. Added unit test in `tests/test_basic.zig`.
