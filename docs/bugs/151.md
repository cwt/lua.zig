# BUG-151 — Table Growth Bypasses `totalbytes` Causing GC Tracking Underflow and Zero Count

- **Severity:** `HIGH`
- **Status:** ✅ CLOSED
- **Location:** `src/lua.zig:1152-1164` (`registerGC`), `src/lua.zig:4718-4736` (`freeGCObject`), `src/ltable.zig:145` (`growNode`), `src/ltable.zig:225` (`ensureArraySize`)

## Defect Summary

1. In `registerGC` (`src/lua.zig:1153`), initial memory consumption of a new table is added to `g.totalbytes`:
   ```zig
   const sz = @sizeOf(lua_Table) + t.array.capacity * @sizeOf(TValue) + t.node.capacity * @sizeOf(Node);
   g.totalbytes += sz + @sizeOf(VMGCObject);
   ```
2. When the table grows in `src/ltable.zig` (e.g. growing the array part via `ensureArraySize`, or the hash part via `growNode` to hold thousands of elements):
   Memory is allocated, but **`g.totalbytes` is never updated with the increased allocation size**. (`ltable.zig` contains no `totalbytes` references at all. Note: there is no `growArray` function — array growth goes through `ensureArraySize`, hash growth through `growNode`.)
3. When the grown table is subsequently collected in `freeGCObject` (`src/lua.zig:4721-4735`):
   ```zig
   const sz = @sizeOf(lua_Table) + t.array.capacity * @sizeOf(TValue) + t.node.capacity * @sizeOf(Node);
   if (g.totalbytes >= sz + @sizeOf(VMGCObject)) {
       g.totalbytes -= sz + @sizeOf(VMGCObject);
   } else {
       g.totalbytes = 0;
   }
   ```
   `sz` reflects the *expanded* capacity (e.g. megabytes). Because this capacity was never added to `g.totalbytes`, subtracting it underflows `g.totalbytes`, clamping it to `0`.

(A secondary accounting gap: a table whose hash part has already grown before `registerGC` runs gets its size recorded correctly, but any growth *after* registration — the normal case for mutable tables — is invisible to the tracker.)

## Impact

Any program that allocates and discards large tables will see `g.totalbytes` repeatedly collapse to `0`.
- `collectgarbage("count")` returns `0` or near-zero memory usage even when megabytes of live objects exist on the heap.
- GC cycle pacing (`gcstep`, debt, and pause calculations) fails completely because the VM believes virtually no heap memory is in use.

## Proposed Fix

Pass `L` or `*global_State` into table resize operations (`ensureArraySize` and `growNode`), and adjust `g.totalbytes` by the delta of newly allocated bytes versus freed bytes.

## Resolution

- Added `g: ?*global_State = null` field to `lua_Table` (`src/lua.zig`), populated in `registerGC`.
- In `src/ltable.zig`:
  - `ensureArraySize`: Computes capacity delta upon `ensureTotalCapacity` and adds `delta_cap * @sizeOf(TValue)` to `g.totalbytes`.
  - `setInt`: Computes capacity delta upon `array.append` and adds `delta_cap * @sizeOf(TValue)` to `g.totalbytes`.
  - `growNode`: Computes net capacity delta upon `t.node` replacement (`(new_cap - old_cap) * @sizeOf(Node)`) and updates `g.totalbytes`.
- Added unit test in `tests/test_basic.zig` verifying that table growth increases `collectgarbage("count")` and subsequent collection does not underflow `totalbytes` to 0.
