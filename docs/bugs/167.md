# BUG-167 — Housekeeping: Stale `src/lua.zig.orig` Backup, Wrong VM Layout Comment, Dead Parity Stubs

- **Severity:** `LOW`
- **Status:** ❌ OPEN
- **Location:** `src/lua.zig.orig` (whole file), `src/lvm.zig:420-428`,
  `src/lua.zig:1175-1202` (`GCObject`, `errorJmp`), `src/lua.zig:1200`
  (`L.gclist`)

## Defect Summary

Three cleanup items found during the 2026-09-08 deep audit:

1. **Stale editor backup in the tree** — `src/lua.zig.orig` (206,649 bytes)
   duplicates the full core file. It is not compiled, but it (a) pollutes
   greps for patterns like `unreachable`/`catch` (it carries its own
   violations), (b) shows up in `hg status` churn, and (c) risks being
   resurrected wholesale. Note BUG-137 (closed) removed `libm.zig.orig` —
   this is the same pattern, missed.
2. **Wrong instruction-format comment** — `src/lvm.zig:420-428` still
   describes the *old Lua 5.4* operand layout ("A: bits 24-31" etc.). The
   actual decode/encode helpers (5.5 layout: 7-bit opcode, A@7, k@15,
   B@16, C@24) are correct — only the comment lies.
3. **Inert parity stubs** — `GCObject` (`lua.zig:1175-1179`), `errorJmp`
   (`lua.zig:1181, 1202`, empty struct, never used), and `L.gclist`
   (`lua.zig:1200`) exist only for C-naming parity. `errorJmp`/`gclist` are
   contradicted by §0.1 rule 3's spirit (no longjmp mechanics); `GCObject`
   is superseded by `VMGCObject` (`lua.zig:1048-1068`).

## Impact

- Confusion for future agents (stale code + wrong comments are red herrings
  during audits); no runtime impact.

## Proposed Fix

1. `hg remove src/lua.zig.orig` (verify it is not referenced anywhere first:
   `grep -rn "lua.zig.orig" src/ build.zig tests/`).
2. Rewrite the `lvm.zig:420-428` comment to describe the actual 5.5 bit
   layout (or simply point at `lua/lopcodes.h`).
3. Delete `GCObject`, `errorJmp`, `gclist` from `lua.zig`; keep
   `VMGCObject` as the single GC node type (single-type-model invariant).
