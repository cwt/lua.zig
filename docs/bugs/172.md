# BUG-172 — Weak-Table Element Count Diverges After Collection

- **Severity:** `HIGH`
- **Status:** ❌ OPEN
- **Location:** `src/lua.zig` (mark-and-sweep `luaC_collectgarbage` weak-table
  sweep), `src/ltable.zig` (weak key/value clearing), reference
  `lua/lgc.c` (`luaC_segenorminal`/weak sweep).
- **Upstream failure:** `lua/testes/gc.lua:249`.

## Defect Summary

After the [BUG-169](169.md) step-budget fix, `lua/testes/gc.lua` proceeds past
the "steps" section and fails in the "weak tables" section:

```lua
a = {}; setmetatable(a, {__mode = 'k'})
for i=1,lim do a[{}] = i end           -- collectable keys
for i=1,lim do a[i] = i end            -- non-collectable keys
...
collectgarbage()
local i = 0
for k,v in pairs(a) do assert(k==v or k..'#'==v); i=i+1 end
assert(i == 2*lim)                       -- gc.lua:249 (fails)
```

The weak-key table should retain exactly the non-collectable entries (and the
collectable keys that survived), but the count is off — the mark-and-sweep's
weak sweep clears/keeps keys differently than the reference.

## Impact

- `lua/testes/gc.lua` fails at line 249 when run standalone.
- Weak-reference tables (`__mode = "k"/"v"`) misbehave in user programs.

## Context

This is the next blocker on `gc.lua` after [BUG-169](169.md) (steps, now
fixed). It is a genuine mark-and-sweep weak-reference defect, separate from the
GC *stepping* semantics.

## Proposed Fix

Reconcile the port's weak-table sweep with `lua/lgc.c`: during a collection, a
weak-key table's keys that are unreachable must be cleared (with the chained-
scatter hash invariants preserved, cf. BUG-118), and weak-value entries' values
cleared only when the value is unreachable. Verify the count with the
gc.lua weak-table section.

## Evidence

```
$ luazig lua/testes/gc.lua
...
weak tables
zig-out/bin/luazig: lua/testes/gc.lua:249: assertion failed!
```
