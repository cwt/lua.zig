# BUG-135 — `OP_SETLIST` per-element `setInt` instead of preallocated direct stores

- **Severity:** [MED]
- **Status:** ⏳ OPEN

- **Location:** `src/lvm.zig:1824-1844`; reference `lua/lvm.c:1907-1930`.
- **Defect:** C computes `last += n`, calls `luaH_resizearray(h, last)` once when
  needed, then writes each value straight into the array slot (`obj2arr`) with a
  barrier. The port loops `ltable.setInt(h, idx, val)` for every element — each
  call re-evaluates array bounds, the `u == len+1` append-promotion branch,
  `clearHashKey`, and possible hash fallbacks.
- **Impact:** Table-constructor-heavy code (`{...}` with many elements,
  `{f()}` spreads) pays avoidable per-element overhead versus the reference; not
  a correctness issue but a hot-path regression against design intent.
- **Proposed fix:** Add a raw bulk-append entry point to `ltable`
  (preallocate to `last`, then copy), mirroring the reference shape.
