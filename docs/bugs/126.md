# BUG-126 — `luaL_ref` / `luaL_unref` free-list divergences

- **Severity:** [MED]
- **Status:** ❌ FALSE POSITIVE

- **Location:** `src/lauxlib.zig:556-606`.
- **Defect:**
  1. On first use `luaL_ref` eagerly writes `t[1] = 0` (freelist-empty sentinel).
     In the reference, slot 1 does not exist until the first unref, so the first
     reference lands in slot 1 (`ref = rawlen+1`). Port numbering therefore starts
     at 2 and the sentinel entry is visible to `pairs(t)` / counted by
     `lua_rawlen` on any user-supplied table.
  2. `luaL_unref` early-outs only for `ref < 0`; `ref == 0` proceeds to write
     `t[0] = old_head` and `t[1] = 0`. C ignores every `ref <= 0`
     (`lauxlib.c`: `if (ref >= 0)` guard is absent in port form), leaving the
     freelist intact.
- **Analysis & Verification:**
  - Inspection of the Lua 5.5.1 C reference in `lua/lauxlib.c:709-716` confirms that `luaL_ref` explicitly initializes `t[1] = 0` on first access:
    ```c
    if (lua_rawgeti(L, t, 1) == LUA_TNUMBER)
      ref = (int)lua_tointeger(L, -1);
    else {
      ref = 0;
      lua_pushinteger(L, 0);
      lua_rawseti(L, t, 1);
    }
    ```
    Then `ref = (int)lua_rawlen(L, t) + 1` produces 2 for the first allocated reference in C as well.
  - In `lua/lauxlib.c:730`, `luaL_unref` uses `if (ref >= 0)`, which matches `if (ref < 0) return;` in `src/lauxlib.zig:567`.
  - The Zig implementation in `src/lauxlib.zig` mirrors the upstream C reference verbatim.
