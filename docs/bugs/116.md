# BUG-116 — `lundump.zig`: `loadInt` decodes counts through the zigzag integer codec

- **Severity:** [CRITICAL]
- **Status:** ✅ FIXED

- **Location:** `src/lundump.zig:100-103` (`loadInt`); secondary `src/lua.zig:3993-3998`
  (error-message mapping).
- **Defect:** `loadInt()` calls `self.loadInteger()`, which applies the *signed*
  zigzag decode (`(cx&1)!=0 ? ~(cx>>1) : cx>>1`) intended for `lua_Integer`
  constants. The C reference (`lua/lundump.c:117-120`) defines
  `loadInt(S) = cast_int(loadVarint(S, INT_MAX))` — a **plain unsigned varint**.
  Every count on the wire (sizecode, sizek, sizep, linedefined, locvars…) is
  therefore misdecoded (e.g. `sizecode = 9` decodes to `-5`).
  Introduced by revision `152:b45c3421f8ce` (2026-08-08, "resolve remaining
  static analysis bugs"), which replaced `loadVarint(maxInt(i32))` with
  `loadInteger()`.
- **Impact:** `lua_load` returns `LUA_ERRSYNTAX` (3) for **every** valid Lua 5.5.1
  binary chunk, including chunks dumped by the reference implementation. All five
  unit tests that load `.luac` fixtures currently fail
  (`bytecode loader`, `VM execution`, `BUG-036 vararg`, `luaL_dostring`,
  `VM arithmetic metamethod`) — `zig build test` reports 127/132 despite
  AGENTS.md claiming 131/131. Additionally, `src/lua.zig:3993-3998` maps **every**
  loader error to the message `"truncated chunk"` (the
  `if (e == error.TruncatedChunk)` branch is dead — both arms produce identical
  text), so diagnostics actively mislead.
- **Proposed fix:** Restore `loadInt` to `try self.loadVarint(std.math.maxInt(i32))`
  followed by a range-checked cast; differentiate the error message per error tag
  in `lua_load`; re-run `zig build test`.
- **Fix:** Restored `loadInt` to call `self.loadVarint(std.math.maxInt(i32))` and differentiated error tag messages in `lua_load` in `src/lua.zig`. All unit tests now pass.
