# BUG-146 — `bit32.extract` and `bit32.replace` Panic on Wrapping Integer Addition

- **Severity:** `HIGH`
- **Status:** ✅ FIXED
- **Location:** `src/lib/bit32.zig:158-162` (`bit_extract`) and `src/lib/bit32.zig:176-180` (`bit_replace`)

## Defect Summary

In `src/lib/bit32.zig`:
```zig
const field = try lauxlib.luaL_checkinteger(L, 2);
const width = lauxlib.luaL_optinteger(L, 3, 1);
try lauxlib.luaL_argcheck(L, field >= 0, 2, "field cannot be negative");
try lauxlib.luaL_argcheck(L, width > 0, 3, "width must be positive");
if (field +% width > NBITS) {
    return lauxlib.luaL_error(L, "trying to access non-existent bits");
}
const f: u6 = @intCast(field);
const w: u6 = @intCast(width);
```

Both `field` and `width` are `i64`. When `width` is a large positive 64-bit integer (e.g. `math.maxInt(i64)`), `field +% width` performs wrapping two's-complement addition, which wraps around to a negative `i64`.
Because a negative number is not `> NBITS` (32), the error branch is skipped.
Execution immediately hits:
```zig
const w: u6 = @intCast(width);
```
Narrowing a large integer to `u6` triggers an unrecoverable runtime integer cast panic.

## Impact

Calling `bit32.extract(x, 1, 0x7fffffffffffffff)` panics and crashes the interpreter instead of cleanly raising `"trying to access non-existent bits"`.

## Proposed Fix

Check for out-of-range bounds independently before arithmetic, or use overflow-safe checking:
```zig
if (field > NBITS or width > NBITS or field + width > NBITS) {
    return lauxlib.luaL_error(L, "trying to access non-existent bits");
}
```
