# BUG-163 — VM Arithmetic Fast Path Shadows User String-Metatable Arithmetic Metamethods

- **Severity:** `MED`
- **Status:** ✅ RESOLVED
- **Location:** `src/lvm.zig:16-26` (`toNumeric`), wired into the arithmetic
  opcode fast paths (`lvm.zig:852-1157`)
- **Reference:** `lua/lvm.c` `op_arith` fast paths use `tonumberns` only (no
  strings); string arithmetic falls through to `OP_MMBIN` →
  `luaT_trybinTM`, where the *string library* has registered `__add` … `__unm`
  on the string metatable (`lua/lstrlib.c:290-341`).

## Defect Summary

In the C reference, `"10" + 1` reaches `trybinTM`, finds the string metatable,
and calls the *library-registered* arithmetic metamethod, which parses the
operand strings. Consequently, if a user replaces one of those metamethods:

```lua
setmetatable("", { __add = function() return "overridden" end })
return "10" + 1    -- C reference: "overridden";  luazig: 11
```

The port instead coerces strings to numbers *inside the VM fast path*
(`toNumeric`, src/lvm.zig:16-26), so `OP_ADD`/`OP_ADDI`/etc. never fall
through to `MMBIN`, and user (or library) overrides of the string metatable's
arithmetic metamethods are silently ignored.

The port *does* register the same `__add`…`__unm` metamethods on the string
metatable (`src/lib/stringlib.zig:245-288`, faithful), but the fast path
shadows them before metamethod dispatch ever happens.

## Impact

1. Observable semantic divergence: `setmetatable("", {...})` arithmetic
   overrides have no effect.
2. Blocks the reference design where string arithmetic is a library feature,
   not a VM feature — future changes to string coercion (e.g. new formats)
   cannot be done library-side.
3. Related to open [BUG-050](050.md) (which documents the *missing* coercion
   opcodes from the opposite audit angle); the two must be reconciled: the
   C design is *coercion-in-library*, not coercion-in-VM.

## Resolution

Ported the reference `tonumberns` boundary into the VM:

1. **New `toNumericNS` helper** (`src/lvm.zig`, next to `toNumeric`): accepts
   only `.integer`/`.number`, returns `null` for strings. This mirrors the C
   `tonumberns` used by `op_arith`/`op_arithI`/`op_bitwise` — the fast path
   must not string-coerce.
2. **All arithmetic opcode fast paths** switched from `toNumeric` to
   `toNumericNS`: `ADDI/ADDK/SUBK/MULK/MODK/POWK/DIVK/IDIVK/BANDK/BORK/
   BXORK/SHLI/SHRI`, the register-register `ADD/SUB/MUL/MOD/POW/DIV/IDIV/
   BAND/BOR/BXOR/SHL/SHR`, and unary `UNM`/`BNOT` (39 call sites). A string
   operand now fails the fast path, so the VM falls through to the paired
   `MMBIN`/`MMBINI`/`MMBINK` opcode the compiler emits after every binary
   expression (`finishbinexpval` in `lcode.zig`), which dispatches
   `luaT_trybinTM` → the string metatable's `__add`…`__unm` (registered by
   `stringlib`).
3. **Numeric FOR loops unchanged** — they keep `toNumeric` because the
   reference `forprep`/`forlimit` coerce string bounds via `tonumber`.

Now `"10" + 1` invokes the library `__add` (or a user override), and
`"2"+1`/`"2"+"3"`/`-"5"` still yield `3`/`5`/`-5` through the string
metatable. Removing `__add` from the string metatable makes `"10"+1` raise
`"attempt to perform arithmetic on a string value"`, exactly like the C
reference.
