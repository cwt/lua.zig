# BUG-119 — `lua.zig`: `reallocStack` cross-thread upvalue fix-up writes the wrong pointer

- **Severity:** [HIGH]
- **Status:** ✅ FIXED

- **Location:** `src/lua.zig:1452-1466` (`reallocStack`, secondary thread loop).
- **Defect:** For each upvalue of every other thread whose `v` fell inside **L's**
  old stack range, the code computes `uv_idx2` from `old_base` but then assigns
  `uv2_.v = &t.stack[uv_idx2]` — the *other thread's* stack — instead of
  `&L.stack[uv_idx2]`. Two failure modes:
  1. If the case genuinely occurs (upvalue into another thread's stack), the
     upvalue is retargeted to an unrelated slot of a different stack → value
     corruption / use-after-realloc on next read or write through the upvalue.
  2. The address-range test runs against memory that was just freed by
     `realloc`; the allocator may hand that range to any later allocation, so a
     *valid* upvalue pointing into some thread's current stack can spuriously
     "match" and be corrupted by this loop.
- **Impact:** Latent stack corruption after any stack growth once cross-stack
  open upvalues exist (or, worse, whenever freed ranges get reused). Not covered
  by tests because the triggering layout is rare.
- **Proposed fix:** Point the fix-up at `&L.stack[uv_idx2]`; better, drop address
  sniffing entirely and store explicit stack-slot indices in `UpVal` for open
  upvalues (the C reference re-links via `correctstack` using index math on
  owned lists only).
- **Fix:** Changed secondary thread loop in `reallocStack` to assign `uv2_.v = &L.stack[uv_idx2]` and skip `t == L` (which was already fixed in the primary loop).
